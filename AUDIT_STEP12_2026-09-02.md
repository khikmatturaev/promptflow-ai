## Findings and targeted fixes

### 1. WebMCP header status could be misleading
**Severity:** Medium UX

The application header previously displayed `WebMCP ready` unconditionally, even before `document.modelContext` was available.

**Fix:** Added `WebMCPStatusBadge` which reads the current WebMCP tool registry and listens for `toolchange`. The header now distinguishes waiting from ready and shows the discovered tool count.

### 2. Package metadata typo
**Severity:** Low release hygiene

The package name was `promptflow-aii`.

**Fix:** Changed package metadata and the pnpm lockfile importer to `promptflow-ai`.

### 3. Historical WebMCP debugging note was potentially misleading
**Severity:** Low documentation

The Step 8 note described the registration lifecycle as the sole explanation for an Inspector showing zero tools. Later validation also identified old/community Inspector API incompatibility.

**Fix:** Marked the document explicitly as historical and clarified the later compatibility discovery. The current README remains authoritative.

## Architecture verification

### Source of truth
- Zustand owns nodes, edges, audit state, layout revision, and agent tool-call telemetry.
- React Flow remains a rendering/interaction layer.
- WebMCP tools mutate through the store rather than maintaining a second architecture state.

### WebMCP
The registry exposes exactly these 12 tools:

1. `add_architecture_node`
2. `connect_architecture_nodes`
3. `update_architecture_node`
4. `remove_architecture_node`
5. `clear_architecture_canvas`
6. `generate_node_boilerplate`
7. `get_architecture_snapshot`
8. `audit_architecture`
9. `auto_layout_architecture`
10. `transform_architecture`
11. `scale_architecture`
12. `fix_architecture`

The batch transform path supports validated multi-operation changes and is the preferred route for agent-generated multi-step architecture changes.

### Reliability
- Registry waits for `document.modelContext`.
- Existing tools are checked before registration.
- Registration is module-singleton based.
- HMR cleanup prevents stale development registrations.
- Abort signals are respected.
- Partial registration failures are cleaned up.
- Tool input bounds are enforced.
- Transform operations are validated sequentially before mutation.
- Agent activity records running/completed/failed states.
- UI has an application-level recovery boundary.

### Performance
- React Flow node/edge change synchronization is batched with `requestAnimationFrame`.
- Position/selection/dimension-only interaction does not unnecessarily invalidate audit state.
- Auto-layout avoids a store update when positions are already correct.
- Agent activity is capped to the latest 30 calls.
- Audit adjacency uses maps/sets rather than repeated graph scans.

### Audit semantics
The architecture audit is deterministic structural linting. It covers empty architecture, entrypoint/compute presence, frontend/backend relationship, data-store reachability, weakly connected components, and duplicate labels.

The UI explicitly labels the score as structural and does not represent it as a security, compliance, availability, or production-readiness certification.
