## 3. Findings and design decisions

### Finding A — CORE 3 simulation was still primarily score/projection based
CORE 3 could model scale pressure, but it did not model explicit failure injection and propagation.

Resolution:
CORE 4 adds a separate Digital Twin model with named load/failure scenarios.

### Finding B — No explicit failure propagation graph
A production architecture review needs to answer what becomes affected when a dependency fails.

Resolution:
CORE 4 traverses dependency direction for failures: if A depends on B (`A -> B`), a failure in B can propagate back to A. The report records affected nodes and propagation depth.

### Finding C — No explicit recovery model
A score alone does not tell an architect how the system should recover.

Resolution:
Each scenario now produces:
- recovery strategy
- recovery actions
- recovery class (`fast`, `moderate`, `slow`, `manual`)

### Finding D — No explicit critical paths / SPOFs in simulation
Resolution:
The Digital Twin report now exposes critical paths and modeled single points of failure.

### Finding E — Simulation must not silently mutate production architecture
Resolution:
All simulation tools are read-only. Hardening is a separate explicit destructive tool. Hardening validates the complete transform batch before mutation and re-runs simulation/audit afterward.

## 4. CORE 4 implementation

### New model
`src/types/digitalTwin.ts`

Defines:
- scenario kinds
- simulation events
- impact severity
- recovery model
- load profile
- scenario results
- complete Digital Twin report

### New engine
`src/lib/digitalTwin.ts`

Provides:
- `runDigitalTwin`
- `simulateLoad`
- `simulateFailure`
- `buildHardeningOperations`

Capabilities:
- load spike modelling
- database failure
- compute failure
- cache failure
- queue failure
- external dependency failure
- regional outage
- dependency failure propagation
- critical path extraction
- SPOF detection
- recovery guidance
- heuristic survivability scoring
- deterministic hardening operation generation

The model is intentionally labeled heuristic. It is not a benchmark, capacity guarantee, chaos-engineering environment, or security certification.

### WebMCP
`src/webmcp/agentOSTools.ts`

Added:
- `run_digital_twin`
- `simulate_failure`
- `simulate_load`
- `apply_digital_twin_hardening`

Input validation is bounded:
- maximum scenario count: 8
- maximum target scale: 1 billion
- bounded node IDs and labels
- supported failure kinds are explicit enums

## 5. Important architectural behavior

The final Core 4 flow is:

User brief
→ semantic Agent OS architecture
→ live graph
→ CORE 3 intelligence
→ Digital Twin
→ failure/load simulation
→ recovery analysis
→ explicit hardening
→ re-validation

The Digital Twin does not create a second editable architecture source of truth. It projects from the current graph and reports what-if results.
